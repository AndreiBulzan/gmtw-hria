## 3.3 — does the repair harm what GMTW-Ro does not measure — **yes, 8.28 points**

*"There is no evaluation of general reasoning, factuality, Romanian
conversational quality, knowledge, safety, or out-of-domain instruction
following after repair. The study therefore demonstrates GMTW recovery, not a
free repair."*

Correct, and now measured. On OpenLLM-Ro's own benchmark suite the repaired
RoLlama3.1-8B-DPO loses **8.28 points** of academic average against its released
base. Three training seeds agree to within 1.7 points on every task.

### Method

The suite is the one OpenLLM-Ro publishes for its own releases, so the base
checkpoint already has a public score to check our run against.

| | |
|---|---|
| harness | OpenLLM-Ro fork of lm-evaluation-harness, pinned at `77e8ac48` |
| protocol | published few-shot ladders — ARC 0/1/3/5/10/25, MMLU 0/1/3/5, Winogrande 0/1/3/5, HellaSwag 0/1/3/5/10, GSM8k 1/3/5, TruthfulQA 0 — raw completions, no chat template, as OpenLLM-Ro scored its releases |
| base arm | `OpenLLM-Ro/RoLlama3.1-8b-Instruct-DPO-2025-04-23`, as released |
| repaired arm | merged `rollama31-dpo_4kv2` adapters, seeds 0, 1, 2; tokenizer loaded from the base |
| held fixed | batch size 64, lm-eval seed 1234, greedy decoding, same hardware and software stack |
| deviation | the fork's task groups cannot be called (`include:` overrides each subtask's name, so the duplicate check rejects every ladder), so each ladder was run rung by rung and averaged by us. Every published task average equals the plain mean of its published rungs, checked on all eight model cards |

### It is not the harness

- **The base arm reproduces OpenLLM-Ro's published numbers.** Academic average
  53.74 against their 53.76; every one of the 23 individual rungs lands within
  1.13 points of its published counterpart. That is on different hardware and a
  newer torch and transformers, so the environment is reproducing theirs, and
  anything the repaired arm does differently is the repair.
- **Both arms load byte-identical tokenizer files** and run the same rungs at
  the same batch size and seed.
- **MMLU is pure log-likelihood ranking** over four fixed options — no
  generation, no output format, no stopping behaviour — and it still loses 11
  points.

### It is not the prompt format

The repaired checkpoints were trained only on chat-formatted prose-then-JSON,
and the published protocol scores raw completions. The loss could therefore
have been an artefact of asking a chat-tuned model to complete raw text. Both
arms were re-run at 5-shot with the model's own chat template, identical
template text on both sides:

| task, 5-shot | format | base | repaired s0 | gap |
|---|---|---|---|---|
| MMLU | raw completion | 56.31 | 42.91 | −13.40 |
| MMLU | chat template | 54.90 | 39.39 | **−15.51** |
| GSM8k | raw completion | 39.20 | 5.84 | −33.36 |
| GSM8k | chat template | 36.85 | 0.08 | **−36.77** |

**The gap widens in the model's own format.** The template costs the base
1.4–2.4 points — the ordinary price of moving a benchmark out of the format it
was written for — and costs the repaired model more than twice that. GSM8k in
chat format is one correct answer out of 1,319. The capability is gone from the
weights, not merely unreachable in the wrong format.

Scope of the control: seed 0, MMLU and GSM8k only. MMLU was chosen because
nothing about prompt format can rescue a log-likelihood ranking; GSM8k because it
is where the damage is largest.

### It sets in at once, together with the repair

Every training run saved an adapter every 50 of its 500 steps. Four were merged
and scored on both harnesses — GMTW-Ro for the repair, MMLU and GSM8k at 5-shot
for the damage:

| step | valid JSON % | U | F_v2 | MMLU | GSM8k |
|---|---|---|---|---|---|
| 0 (base) | 22.4 | 0.430 | 0.035 | 56.31 | 39.20 |
| **50** | **100.0** | **0.751** | **0.695** | **42.24** | **4.70** |
| 100 | 99.4 | 0.763 | 0.703 | 42.30 | 5.16 |
| 250 | 99.8 | 0.764 | 0.707 | 42.95 | 6.44 |
| 400 | 100.0 | 0.777 | 0.713 | 42.84 | 5.61 |
| 500 (final) | 100.0 | 0.760 | 0.678 | 42.70 | 5.13 |

**Everything happens in the first 50 steps** — 800 examples, a tenth of the
schedule. By then valid JSON is at 100% and MMLU has already lost 14 points.
Neither axis moves afterwards.

So stopping early cannot buy the repair without the loss: at this learning rate
(1e-4) repair and forgetting are one event, not two processes with different
time constants. Any mitigation has to change the recipe — learning rate, replay
of general instruction data, adapter size — and that needs new training runs.

Steps 50–400 are seed-0 intermediate checkpoints; step 500 is the mean of three
seeds. The schedule is cosine over 500 steps, so checkpoint-50 is not a run
*scheduled* for 50 steps — its learning rate never annealed. It is a lower bound
on what a short run achieves, which is the conservative direction for this
conclusion.

→ `datagen/results/dose_rollama31_c{50,100,250,400}/`,
  `datagen/retention/results/dose_rollama31_c*/`

### What the failure looks like

GSM8k writes its answers out, so its samples show the mechanism:

| GSM8k, 5-shot | accuracy | outputs that loop | uses the `####` answer marker |
|---|---|---|---|
| base | 39.20% | 32.5% | 69.4% |
| repaired, seed 0 | 5.84% | 54.5% | 27.3% |

The repaired model stops following the answer format its own few-shot examples
demonstrate, and degenerates into repetition with token-level corruption.
Excerpts from wrong answers, verbatim:

```
… pentru 2 dolari pe între-înțărcuită înainte de a începe să-înțe-înțe-înțe-înțe-înțe …
… Înainte de a da răspunsul, a găsit 8 șurubzi. În cele din urmele, Steve a găsit 28 șurubzi …
… Întrețiună: Ștefteșteună << 45/2=<< 45/2=45/2*<< 45/2=<< …
```

Not wrong arithmetic — broken text.

## Two issues found along the way

Found while making the retention comparison like-for-like. **Neither changes the
3.3 result.** Both change numbers outside it — in the manuscript or the repair
tables — and should go to whoever owns those sections before submission.

### The RoGemma2 repair rows compare a serving fix against a serving bug

Merged repaired checkpoints have their stop tokens aligned to their chat
template at merge time. The released RoGemma2 checkpoints were scored as shipped
(`eos_token_id = 1`, a token their template never emits), so they never stop
generating:

| | median output length | outputs with verbatim repetition |
|---|---|---|
| RoGemma2-9B-DPO, released | 11,373 chars | 155 / 500 |
| google/gemma-2-9b-it | 868 chars | 0 / 500 |

On identical weights (v1-corpus RoGemma2-DPO, seed 0), the stop-token alignment
alone moves valid JSON from **54.8% to 99.6%** and U from **0.599 to 0.835**.
Part of both RoGemma2 repair deltas is therefore serving rather than training,
and the same defect affects the observational RoGemma2 vs gemma-2-9b-it
comparison. Fix: re-score the released RoGemma2 checkpoints with aligned stop
tokens.

→ `datagen/results/rogemma2-*_eos1/` (unaligned) against
  `datagen/results/rogemma2-*_4k_s*/` (aligned)

### GMTW-Ro scorer fixes exist only as uncommitted changes

Fixes for checks that recorded scorer exceptions as rule violations — unhashable
plan values, non-string answers, and a `C_HIGH_MORNING` checker that was never
implemented and so scored 0% for every model — exist only as uncommitted changes
in one local checkout of `gmtw-hria`. **No reported number uses them.**
Re-scoring existing RoLlama3.1-8B-DPO outputs with them:

| run | U, reported | U, re-scored | change |
|---|---|---|---|
| repaired s0, standard 500 | 0.7746 | 0.7865 | +0.012 |
| repaired s0, adversarial 300 | 0.5936 | 0.6098 | +0.016 |
| base, standard 500 | 0.4300 | 0.4402 | +0.010 |
| base, adversarial 300 | 0.3483 | 0.3734 | +0.025 |

The base gains more than the repaired model on the adversarial split, so ΔU
there shrinks by about 0.009. Small, but it moves in one direction, and every
GMTW-Ro number in the paper should come from one committed scorer.
